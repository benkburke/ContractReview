# Fix: claim evaluation fails when the model asks for a coverage level but lists no tiers
Status: done 2026-11-02 (approved by human, per D-035)
- **Problem:** evaluating a claim throws `ChatFailedException(MalformedOutput)` ("does not match the schema") from `OpenRouterChatClient.EvaluateAsync`; the log does not say which rule failed.
- **Root cause (best hypothesis):** prompt rule 5 (`ClaimSystemPrompt`) makes the model set `needsCoverageLevel: true` with tier names "found in the contract"; when the excerpts name no tiers it returns an empty `coverageLevelOptions`, which `LlmClaimAnswer.FindViolation` rejects (`ViolationNeedsLevel`). Temperature 0 makes the retry identical, so both attempts fail.
- **Planned change (per D-035):** (1) `ChatWire.ParseAnswer` normalizes `needsCoverageLevel: true` + empty options to `false` before `FindViolation` (status and follow-up question kept as returned). (2) `OpenRouterChatClient` logs the violation constant (never the content) in its malformed-output warning; JSON/schema failures log a distinct reason. (3) Prompt rule 5: if no tier names appear in the excerpts, set `needsCoverageLevel` to false and ask for the coverage level in `followUpQuestion`. No endpoint, schema or UI change.
- **Owner:** `backend` (Infrastructure/Chat only).
- **Regression test:** unit test in `ContractReview.UnitTests` (add `InternalsVisibleTo` for UnitTests in Infrastructure if needed) or an integration test with a stubbed `HttpMessageHandler`: chat content with `needsCoverageLevel: true`, `coverageLevelOptions: []`, status `InsufficientInformation` → `EvaluateAsync`/`ParseAnswer` returns an answer with `NeedsCoverageLevel == false` instead of throwing.
