---
name: feature
description: Full workflow for anything that adds or changes an endpoint, hub method or event, database schema, auth rule, or user-facing flow - spec, contract, parallel build, verify, document, review.
---
Run the Feature workflow for: $ARGUMENTS (if empty, use the next unchecked roadmap item).

0. **Roadmap.** Match the work to an item in `specs/roadmap.md`. Thin-path items come first; if the human asks for a depth item or new work before the thin path is done, say so in one line, and if they confirm, record the choice. Work that is not on the roadmap gets added to it first.
1. **Spec (you only).** Explore with Grep/Glob (or `scout` across many folders), draft in plan mode, then exit plan mode and write `specs/<kebab-name>.md`. Line 2 is `Status: draft`; line 3 is `Roadmap: T<n> (thin)` or `D<n> (depth)`. A thin item's spec stays within its one-line scope: happy path, plus the rules that protect money, data and access; everything else goes in "Out of scope" and onto the roadmap's Depth list. Sections: context; sides involved (backend, frontend or both); acceptance criteria as Given/When/Then; endpoints with request/response DTOs and status codes; validation rules and limits for every input (required, min/max, length, format, allowed values); hub methods/events with payloads if realtime; auth and policies per `docs/project.md`; domain model (commands and queries by name; aggregates, value objects, invariants and domain events only where business rules exist; "plain CRUD" otherwise); data model changes; accessibility notes for new UI; out of scope; open questions. Keep it as short as the change allows. Stop for approval. Record every answer, change and choice the human gives as a decision, and cite the IDs in the spec. Only when no open question is left, set `Status: approved <date>`.
2. **Contract** (only when both sides are involved and the HTTP or hub contract changes). Dispatch `backend` with a contract-slice task. When it reports, run `cd frontend && npm run gen:api` yourself (and note any `src/realtime/contracts.ts` change for the frontend task). Show the generated diff with `git diff --stat`.
3. **Route.** Tag each task simple / standard / complex and pick `model` and `effort` from the table in your agent file; list the routing in one short block.
4. **Build.** Dispatch only the involved sides. Both sides: `backend` and `frontend` in the SAME turn so they run in parallel. Wait for both reports. Failures follow the loop caps in your agent file. A contract change goes back to step 1 for approval.
5. **Verify and document.** In the SAME turn, dispatch `tester` with `TEST MODE: thin` for a thin-path item or `TEST MODE: full` for a depth or hardening item (happy-path pass, then failure scenarios for that mode, then `verify --e2e` once) and, only if the API, hub events or setup changed, `documentor` with the endpoints or setup steps to cover. Route defects to the owner with the tester's one-line summary each; after a fix, re-dispatch `tester` only for the affected tests and the gate.
6. **Review.** Run `node scripts/verify.mjs --e2e` (returns the cached result when nothing changed) and `git diff --stat`. Present: what was built, verify result, coverage gaps from `specs/coverage/<feature>.md`, and a proposed Conventional Commit message. Wait for approval, commit, set `Status: done <date>`, tick the roadmap item, and suggest `/clear`. Record any choice the human made at review.
